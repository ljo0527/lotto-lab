## 2026-10-26 · 구멍 난 자료로 굳은 1247회 순위 행 때문에 `check-rank` 가 계속 실패

### 증상
- 10-24부터 CI `당첨 순위 독립 검증`(check-rank)이 매 실행 실패: `brute.lotto R=1247 popf.of 4933623 ≠ 전수 4933622`, `all.lotto R=1247 popf.of …`,
  `page.lotto R=1247 fitPop A/B/bounds ≠ params`(A.beta1 페이지 0.00069 · 기록 −0.00026), `page.zOf.core R=1247` 5건. 11회차 구멍을 고친 뒤(`15f48cc`)의 시험·main 실행(10-26)에서도 같은 값으로 남았다.
  배포는 `always()` 라 계속됐지만 실행은 빨간 X.

### 원인 (확정)
- 1247회 행과 파라미터는 10-24 실행(`e4912f0`)이 **11회가 빠진 자료**로 처음 계산해 저장했다 `[근거: 그 실행 로그 «1등 조합이 빠진 회차: 11»]`.
  `rank-track` 은 append-only 라 기존 행을 덮지 않고, 마지막 4행 재계산이 다르면 경고만 내고 저장값을 둔다 — 10-26 main 실행 로그
  «기존 행과 다시 계산한 순위가 다릅니다: 1247 — 기존 행을 그대로 둡니다», «기존 파라미터와 … 1247» `[근거: run 40255241907]`.
- `check-rank` 는 온전한 자료로 독립 재계산하므로 저장값과 어긋난다. 숫자도 맞는다: popf 의 «of»(필터 통과·이전 1등 제외 조합 수)는 회차가 갈수록 줄거나 같아야 하는데
  1246 행 4,933,622 → 1247 행 4,933,623 으로 하나 늘었다 = 빠진 11회 1등 조합이 제외 목록에 없었다. fitPop 의 A.beta1 도 1246(0.00067)·1248(0.00072) 사이여야 할 값이 −0.00026 이었다.
- 같은 두 실행이 쓴 다른 장부(주간 추천·모의 원장·검증 보드·등수 분포)는 다음 온전한 실행(`efaf8bb`)이 다시 계산했고 독립 검사도 통과했다. append-only 로 굳은 것은 이 두 항목뿐이다.

### 수정 (수리)
- `brief/rank-lotto.json` 의 1247 행과 `brief/rank-params-lotto.json` 의 `"1247"` 항목을 지웠다(파일 형식 그대로, 다른 행은 손대지 않음).
  다음 실행의 `rank-track` 이 1247 을 «새 회차» 로 보고 온전한 자료(구멍 검사 `assertLottoRows`·`assertPageDb` 통과)로 다시 계산해 적재한다.
- `rank-track` 의 결정성·파라미터 경고 문구에 이 수리 절차를 가리키는 말을 붙였다.
- 수리 절차(일반): 자료가 바로잡힌 뒤 «기존 행과 다시 계산한 … 다릅니다: R» 경고와 독립 검증 불일치가 R 에서 함께 계속되면, 그 R 의 행·파라미터만 지우고 커밋한다.
  자료가 그대로인데 결정성 경고가 나면 지우지 말고 원인(엔진·페이지 변경)을 먼저 찾는다.

- 수정 후: 아래 시험 가지 실행 결과를 적는다.

### 남은 위험
- 1248회 추천은 구멍 난 실행(10-25)이 처음 냈고, 이후 온전한 실행(10-26)이 다시 계산해 바꿨다. 그 사이 구매한 번호가 있으면 지금 사이트의 추천과 다를 수 있다. `[추론]`

## 2026-10-26 · 최신 회차 끝자리가 7이면 11회차 자료가 빠진 채 추천·검증이 계산된다

### 증상
- 2026-10-24·25 실행(최신 1247)에서 `rank-track` 경고 «1등 조합이 빠진 회차: 11», `check-rank` 불일치 다수, `check-sim` «draws 기록=1246, 독립재계산=1247», 모의 원장 결정성 불일치가 났다.
  그런데도 `continue-on-error` + deploy `always()` 구조라 그 자료로 만든 결과가 커밋·배포됐다. 직전 실행(최신 1246 이하)에는 없던 현상이다.
- 구멍 하나(11회)가 추천을 크게 흔든다: 최신 1237(끝자리 7)로 자른 같은 자료에서 구멍 난 쪽과 온전한 쪽의 로또 추천 10줄 중 겹치는 것은 4줄뿐이었다(아래 검증 ③).

### 원인 (확정)
1. **수집 코드가 11회를 어느 창에도 넣지 않았다.** 수정 전 `index.html` `fetchRange`(a341629 기준 817~835행)는 센터를 `to, to-10, …` 로 «내려오며» `e ≥ from+7` 까지만 깔고
   맨 아래에 센터 1 한 개를 따로 얹었다. 동행복권 API 는 `center-5 .. center+4` 10건을 준다. 최신이 1247이면 마지막 센터가 17(12~21)이고, 그 아래는 센터 1 뿐이라 **6~11회가 센터 1 의 몫**이 된다.
   센터 1 이 6~10 을 못 주면 11 은 어느 창에도 없다. 끝자리가 2~6 이면 마지막 센터가 12~16 이라 빠지는 구간이 6~10 이내라 재시도가 메우고, **끝자리 7 일 때만 11 이 남는다.**
2. **실 API 와 모의 API 가 달랐다.** 실 API 는 하한에서 창을 위로 밀어 센터 1 도 1~10 을 준다 `[근거: 2026-10-26 GET center=1 → 10건 1..10 확인, center=3 → 1..10]`.
   그래서 실제 사용자 브라우저에서는 센터 1 이 1~10 을 주고 재시도 한 번(`syncData` 의 «누락 재시도», 수정 전 877~883행)이 11 을 채워 문제가 안 났다.
   반면 CI 의 계산 스크립트 5개의 모의 API(`mockRoutes`)는 창을 `center-5 .. center+4` 로만 잘랐다
   (`rank-track.mjs:148`, `backfill.mjs:142`, `validate.mjs:165`, `weekly-brief.mjs:154`, `rank-tiers.mjs:191`) → 센터 1 이 1~5 만 줌.
3. **재시도가 한 번뿐이었다.** 빠진 6~11 을 «가장 작은 빠진 회차 ~ 가장 큰 빠진 회차» 한 덩어리(6~11)로 한 번 부르면 센터 6 이 1~10 을 줘서 6~10 만 채워지고 11 이 남았다. 두 번째 재시도가 없었다.
4. **구멍을 잡는 검사가 없었다.** 페이지는 구멍이 남아도 «최신 N회까지 동기화됨» 이라고 했고, 스크립트는 `DB.draws[DB.latest]` 가 생기면 1.5초 쉬고 곧바로 계산했다(수집이 끝났는지·연속인지 확인 없음).
   Node 쪽 수집(`getLotto`)은 센터를 `Math.max(c,3)` 로 눌러 실 API 하한 이동에 기대고 있었는데 그 연속성도 확인하지 않았다.
- 재발 조건: 최신 회차 끝자리 7 (다음은 1257). `[근거: check-collect 스윕 — 수정 전 index.html + 예전 모의로 최신 1240~1249 중 1247 만 «구멍 1개 (11)»]`

### 수정
- `index.html`: `rangeCenters(from,to)` 신설 — `from` 에서 위로 10씩 창을 빈틈없이 깔고 마지막 센터만 `to` 로 눌러 «아직 없는 회차»를 센터로 부르지 않는다(하한 밀림에 기대지 않음).
  `fetchRange` 는 이를 쓰고, 센터 목록을 받는 `fetchCenters` 로 분리. `syncData` 의 누락 재시도는 «빠진 구간별로, 빈 회차가 없어질 때까지, 진전 없으면 멈춤, 최대 4번». 끝내 남으면 `saveDB()` 후 «동기화됨» 대신 오류 상태와 `false` 를 돌려준다.
- `scripts/data-guard.mjs`(신규): `lottoApiWindow`(모의 API 를 실 API 처럼 — `lo=max(1,c-5)`, 10건), `assertLottoRows`(수집 직후 1..latest 연속성), `assertPageDb`(페이지 DB 1..latest 연속·`DB.latest` 일치, 최대 30초 폴링 후 실패). 검수 후 보강: DB 출처(`DB.source`)가 «동행복권 공식 API» 일 때만 통과 — 새 컨텍스트에서 수집이 실패하면 페이지가 커밋된 `lotto-history.json` 으로 DB 를 통째로 바꾸는데, 그 파일이 연속이고 최신이 같으면 구멍·최신 검사만으로는 수집 회귀가 가려지기 때문.
- 계산 스크립트 5개(`rank-track` `rank-tiers` `validate` `weekly-brief` `backfill`): 모의 창을 `lottoApiWindow` 로 교체, `getData` 에서 캐시를 읽은 직후·새로 받은 직후(캐시 쓰기 전) `assertLottoRows`, 로또 페이지를 띄운 직후 `assertPageDb`.
  실패하면 `실패: [자료 구멍] …` 로 종료 코드 1 — `weekly-brief` 는 워크플로에서 `continue-on-error` 가 없어 커밋 단계 전에 잡이 멈춘다. 캐시 읽기 단계의 실패는 «캐시 읽기 실패, 새로 받습니다» 로 이어져 구멍 난 캐시를 버린다.
- `scripts/check-collect.mjs`(신규): 가짜 자료로 `index.html` 의 수집이 최신 끝자리 0~9 모두에서 1..latest 를 채우는지, 모의 API 3종(legacy·real·strict)에서 보는 회귀 검사. 가드의 판정과 DB 직접 계산이 일치하는지도 교차 확인.
- (로컬 도구, git 밖) `.lab/snap.mjs` 의 모의 창도 같은 규칙으로 맞춤.

### 남은 위험
- (10-26 해소: 1247 행·파라미터를 지워 다시 계산 — 위 «1247회 순위 행» 항목. `check-sim` 은 다음 실행에서 통과해 손대지 않았다) 10-24·25 실행이 구멍 난 자료로 저장한 append-only 항목은 수정만으로 고쳐지지 않을 수 있다. 예: `brief/rank-lotto.json` 의 `wonIdx[10]=null`(이 배열은 매 실행 다시 만들어져 채워진다), 그러나 `rank-lotto.json`/`rank-params-lotto.json` 의 1247 행과 `sim-lotto.json` 의 과거 행은
  «기존 행을 그대로 둡니다» 규칙으로 남는다. 다음 실행의 `check-rank`/`check-sim` 불일치가 계속되면 해당 행을 지우고 봇이 다시 계산하게 할지 결정이 필요하다. `[확인 필요]`
- 현재 커밋된 1248회 추천(`brief/latest-summary.json`)은 11회 없는 자료로 계산됐을 수 있다. 1248회 추첨(10-31) 전 다음 실행이 온전한 자료로 다시 쓰지만, 이미 구매한 번호와 다를 수 있다. `[추론]`
- `check-collect` 는 워크플로에 넣지 않았다(로컬 회귀용). CI 에 넣을지는 소유자 결정.
- 실 API 의 상단 경계(center = 최신 회차 근처)는 이번에 새로 확인하지 않았다. `rangeCenters` 는 마지막 센터를 `to` 이하로 눌러 «없는 회차 센터» 를 피한다.
